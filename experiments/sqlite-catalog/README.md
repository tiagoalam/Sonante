# Sonante SQLite catalog experiment (B2B-2B)

Independent Rust prototype. SQLite access uses `rusqlite` 0.41.1 with its `bundled` feature, so SQLite is compiled from the source shipped by `libsqlite3-sys` instead of linking to a system SQLite installation. This requires a target C compiler. The Linux-specific secure filesystem scanner is isolated in `src/scanner.rs`; a Windows scanner backend is not implemented yet, so this is not a portable Windows implementation.

Schema v4 preserves `sources`, `tracks`, and `track_metadata`, and adds `track_metadata_extra_artists` for additional track and album artist values. The first artist remains in the existing v3 text column; later values are stored with role and ordinal, preserving order without ambiguous separators. V3-to-v4 is transactional and non-destructive. Earlier v2 databases migrate sequentially through v3 to v4. Legacy tracks have no metadata row until the next explicit verify/rebuild operation. Opening the catalog does not scan or parse files.

Root and relative path identity is held in BLOBs: Linux uses exact native `OsStr` bytes; the format reserves Windows UTF-16LE code units, but a Windows scanner is not implemented. Display names remain UTF-8 text. Foreign keys are enabled; journal mode is WAL and synchronous is FULL.

On Linux, a validated schema-v1 database migrates transactionally through v2, v3, and v4 without scanning the filesystem. IDs, rows, generations, timestamps, and the source AUTOINCREMENT sequence are preserved. Migration rejects any v1 identity path containing U+FFFD because the old lossy representation cannot distinguish a literal replacement character from bytes previously replaced during conversion; the database is left intact. Other platforms reject v1 migration rather than assuming which platform produced its path strings. Future schema versions and unknown or non-native path formats are rejected without rewriting the database.

Each operation walks only its selected root, does not follow symlinks, and collects a complete listing before opening a write transaction. On Linux, eligible WAV, AIFF, FLAC, MP3, Ogg Vorbis/Opus, and MP4-family AAC/ALAC files are opened through the scanner's directory-descriptor-anchored, no-follow path and checked against their scan-time identity and attributes before and after parsing. The parser receives a `BufReader<File>`; it never reopens a path by joining it to the root. Descriptors are short-lived, one extraction at a time. Non-Linux builds have no secure scanner backend yet.

Adds insert one source, tracks, and extraction results atomically. Verify/rebuild changes and removals are committed together only after a complete scan and generation validation. Errors leave old records intact. `open()` initializes/opens SQLite only and never scans. Removal deletes database rows only. Source roots whose canonical paths are equal or ancestor/descendant are rejected.

Lofty 0.25.4 is pinned with `default-features = false` and `id3v2_compression_support`; cover art parsing is disabled. WAV PCM and FLAC use logical parser version 2, MP3 uses version 3, and Ogg candidates (`.ogg`, `.oga`, `.opus`), AIFF (`.aif`, `.aiff`), and MP4 candidates (`.m4a`, `.mp4`) use versions 1 in their respective families. Adding a parser family retries earlier unsupported candidates of that family without reprocessing unchanged records from other formats. Ogg codec selection is based on the identification packet, not the extension: Vorbis and Opus are parsed; Speex is recorded as unsupported. MP4 codec selection uses Lofty's parsed audio sample entry: AAC and ALAC are parsed, while other/unknown codecs are unsupported. `.mp4` is treated as an audio candidate by suffix; a video-only MP4 is consequently recorded as a parse failure rather than interpreted as audio. The Opus sample-rate value follows Lofty's `OpusHead` input sample-rate property, not the codec's 48 kHz decode clock; an unspecified/zero header value remains absent. It extracts RIFF INFO from WAV PCM, AIFF ID3v2 with AIFF text chunks as per-field fallback, Vorbis Comments plus STREAMINFO from FLAC, Vorbis Comments from Ogg Vorbis/Opus, MP4 `ilst` fields and AAC/ALAC properties, and ID3v2.3/2.4, ID3v1 fallback, and Lofty-supported APE tags from valid MPEG Layer III files. For MP3, one complete tag source is selected deterministically: ID3v2, then APE, then ID3v1. Fields are never merged across conflicting tag sources. Repeated artist values exposed by Lofty's tag API are preserved in order; strings are never split by punctuation. Non-Layer-III MPEG data in a `.mp3` file is marked unsupported; malformed files are a parse failure, distinct from valid audio without recognized tags. Other indexed audio formats remain unsupported and are not opened for parsing. Failed attempts are remembered for the same file signature and format-specific parser version; explicit rebuild, changed size/mtime, or a relevant parser-version change makes them eligible again. Failed attempts retain last-successful metadata, but its saved file signature marks it stale for a changed file. A successful parse without tags replaces the successful result with an empty-tag result while retaining available technical properties.

Synthetic WAV, FLAC, AIFF, AAC-in-M4A, and ALAC-in-M4A fixtures exercise parsing; the AAC and ALAC containers were generated from synthetic tones with ffmpeg and independently checked with ffprobe. Tests use Lofty's writer to add MP4 `ilst` metadata. For the AAC fixture, Lofty's raw audio-track duration includes encoder priming (173 ms), while ffprobe's edit-list presentation duration is 150 ms; no duration correction is inferred in this prototype. Short Ogg Vorbis, Opus, and Speex streams were also generated from synthetic tones with ffmpeg and checked with ffprobe; tests use Lofty's writer to add Vorbis Comments. The Opus fixture declares a 44.1 kHz input rate in OpusHead while ffprobe reports the 48 kHz decoding rate, verifying the distinction. The MP3 base fixture is a short silent MPEG Layer III stream generated locally with ffmpeg; test tags are written through the pinned Lofty writer. Older B1 fixture files with arbitrary synthetic bytes remain used only for catalog enumeration. File signatures remain size and nanosecond mtime only: a same-size rewrite whose mtime is restored can be missed. Metrics distinguish filesystem files examined, files opened for extraction, files passed to the parser, successes, no-tag results, unsupported formats, failures, parser duration, and metadata rows written. Fixture timings are not representative of real libraries or other codecs.

Run: `cargo test --offline -- --nocapture`.

## B1.6 concurrency contract

A verify/rebuild captures the source generation, enumerates the filesystem without a SQLite write transaction, then starts `BEGIN IMMEDIATE` and compares the persisted generation before applying any DML. If the source disappeared or its generation advanced, the operation returns a stale-result error and the transaction is rolled back. Removal uses its own immediate transaction, so a scan cannot recreate a removed source. Independent SQLite connections coordinate through SQLite locking and the persisted generation, not an in-memory mutex. Per-source filesystem scans can overlap; SQLite write commits serialize briefly. No retry loop is used.

## B2C-2 derived browsing

`albums_for_source`, `artists_for_source`, `tracks_for_album`, and `albums_for_artist` derive navigation data from schema-v4 rows; they do not persist album/artist entities and do not scan, parse, or open audio files. Each API loads tracks, metadata, and ordered extra artists for one source with a single joined SQLite statement, so the result comes from one SQLite read snapshot and does not use per-track queries. Grouping is O(n log n) in the number of source tracks and uses O(n) working memory. Album grouping is source-scoped and uses normalized album title, the explicit ordered ALBUMARTIST set, and relative-directory context. The final directory component is collapsed only for conventional `CD 1`, `Disc 2`, or `Disk_03`-style disc folders. Other subdirectories may remain separate groups. If the same title/album-artist key appears in multiple directory contexts, each context is kept separate and the albums are marked ambiguous. Missing ALBUMARTIST is not inferred from track artists; such groups are marked ambiguous. Tracks without ALBUM do not create groups. Conflicting dates are retained and mark a group ambiguous rather than proving distinct editions. Artist grouping trims and lowercases text but does not remove accents or merge spellings beyond that rule. Multiple artist values and their track/album roles remain on each returned track. Stale last-success metadata is returned with an explicit stale marker and contributes to album/artist stale counts. `AlbumId` values are deterministic for current metadata and paths, source-scoped, and mutable after metadata or path changes; they are not permanent IDs. A synthetic 5,000-row database test measured one read query for album listing and one for artist listing; timings are recorded by the test and are not a production benchmark.

## B2C-3 synthetic validation

`b2c3_synthetic_scale_benchmark` is an ignored, explicitly invoked test. It inserts synthetic v4 rows directly into temporary SQLite catalogs (no audio files), then takes three warmed-query measurements per operation and reports min/median/max in microseconds. The test does not flush operating-system caches, so “reopen + first query” is not a cold-disk measurement. Memory was not reported because this harness does not provide a reliable per-operation measurement. Each measured browsing API uses one joined SQL statement; the fixture has one primary artist value per role, so joined rows equal track rows. All APIs derive their result from the complete source batch.

The three-repeat ranges were narrow for most operations (for example, at 100,000 tracks the joined read was 1,074.7–1,081.5 ms and album listing was 1,458.2–1,511.0 ms). This is an in-process test-profile measurement, not a release-build or real-library performance guarantee. A request for one 50-track album loads and groups every track in its source before returning only 50. Repeated album navigation repeats the source-wide read and grouping. The query plan uses the tracks `(source_id, relative_path)` primary-key index and the metadata/extra-artist primary keys; there is no per-track SQL query or filesystem access. This is the confirmed navigation bottleneck. A narrower candidate lookup must preserve Unicode grouping semantics, while an in-memory grouped view would need generation-based invalidation. Persistent materialization is not justified by this experiment alone and remains out of scope.

Additional deterministic fixtures cover multidisc tags without disc subfolders, Unicode case variants without accent folding, a compilation without explicit `ALBUMARTIST`, removal of every track in a group, and a browse held at its first SQL row while another connection commits a full metadata update. That browse returns one internally consistent old snapshot; the next query returns the confirmed new snapshot. These grouping rules reduce known collisions in tested fixtures but do not identify editions perfectly without external identifiers.

## B2C-4 immutable source navigation view

`Catalog::source_library_view(source_id)` builds a temporary, immutable `SourceLibraryView` from one joined SQLite statement snapshot. The query includes the source generation; after grouping and building album/artist indexes, construction checks that the persisted generation is still current and returns an error if the source changed or disappeared during construction. No database statement or lock is retained by the view. Its `albums()`, `artists()`, `tracks_for_album()`, and `albums_for_artist()` methods only access owned memory. A consumer can call `Catalog::is_source_library_view_current(&view)` for a scalar generation check; `false` means the caller must explicitly build a replacement before presenting the snapshot as current. Existing `Catalog` browsing methods remain available and retain their prior behavior. No global cache, background task, table, or schema change was added.

The view uses the existing album and artist grouping functions. Album-track indexes are sorted once using disc, track, then native relative-path order. Artist-to-album indexes use the same normalized keys as `albums_for_artist`; identities remain source scoped, and all metadata stale markers and path representations remain owned in the snapshot. A view remains readable and internally consistent after a later update/removal, but its currentness check reports `false` after the persisted source generation changes or the source is removed. The generation check is a point-in-time query; a writer can commit immediately afterward, so consumers should check when they need freshness and rebuild explicitly.

Recommended consumer lifecycle: build a view when a source is selected, retain it for navigation within that source, and use its in-memory methods for album/artist transitions. On an explicit catalog refresh or a UI boundary that requires freshness, check `is_source_library_view_current`; if false, discard the old view for current presentation and explicitly request a new one. The old snapshot itself remains safe to inspect, but the library does not silently rebuild it.

`b2c4_source_library_view_release_benchmark` is an ignored synthetic benchmark, run with `cargo test --release --offline --locked b2c4_source_library_view_release_benchmark -- --ignored --nocapture --test-threads=1`. It builds catalogs of 5k, 25k, 50k, and 100k tracks without audio files, uses seven batched samples of 1,000 in-memory navigations per operation, and reports min/median/max. View construction is timed separately (initial build plus three rebuild samples); opening the catalog connection and building the first view after reopening are also timed separately. “List” timings consume the returned album/artist references, and the track query consumes all 50 returned references. Generation validation uses a separate scalar SQLite query. These synthetic rows have one artist value per role and exercise source-wide album grouping.

The B2C-4A release measurements for five sequential 50-track album navigations were 74.09, 398.10, 804.64, and 1,676.21 ms at those four catalog sizes. Building the view once (using the median of three rebuild samples) and performing the same five navigations took approximately 23.09, 116.89, 249.90, and 534.87 ms respectively; the five in-memory navigations add about 0.25 ms per 1,000 such five-navigation batches, or roughly 0.00025 ms for the measured batch. That is about 68–71% less elapsed time for this five-navigation sequence. A single view build is more expensive than one legacy navigation call, so the improvement depends on reusing the view. Listing timings are sub-microsecond and therefore are especially sensitive to hardware, CPU frequency, compiler, and benchmark noise; treat them as scale indicators, not user-visible latency guarantees. Measurements were release-profile runs on synthetic catalogs, not real libraries. No reliable per-view heap measurement was available: process RSS would include SQLite, fixture generation, allocator state, and other process memory, so exclusive view memory is not claimed. The view's retained data and indexes are O(tracks + albums + artists); peak build memory also includes temporary grouping structures.
